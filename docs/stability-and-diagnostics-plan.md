# 安定性改善・接続診断・録画状態表示の実装計画

作成日: 2026-09-22
対象: v0.9.5 のレビュー結果
状態: 初期実装済み。実機・Extension Development Hostでの確認は未完了。

## 1. 目的と対象範囲

端末切替や通信失敗時にも操作先・録画対象を正しく保ち、接続できない理由と録画の進行状態を利用者が判断できるようにする。

対象は次の不具合6件と追加機能2件に限定する。

| ID | 優先度 | 対応内容 |
|---|---|---|
| BUG-01 | 高 | 接続処理の競合による選択端末・入力先・表示先の不一致 |
| BUG-02 | 高 | 録画開始待ち中の端末切替・非表示・破棄への対応 |
| BUG-03 | 中 | Android入力コマンドの失敗検知 |
| BUG-04 | 中 | 旧端末の画面サイズが残る問題 |
| BUG-05 | 中 | 不完全なMP4を正常判定する問題 |
| BUG-06 | 中 | 入力RPCのタイムアウト不足 |
| FEAT-01 | 高 | 接続診断 |
| FEAT-02 | 中 | 録画時間・停止処理中の表示 |

画面回転、IME入力、複数端末の同時表示、操作マクロ、CIの変更、WDA設定先の特定改善は今回の対象外。大規模なクラス分割や新規依存の追加も前提にしない。

- `npm test` は58件成功。これはテストランナーの集計値であり、個々のassertの総数ではない。
- BUG-01・02・04は非同期応答や端末状態を制御したモックで再現した。
- BUG-03は同じシェル送信経路で失敗コマンドを実行し、成功と判定されることを確認した。実Androidでの失敗条件は未検証。
- BUG-05はファイル読み込みを模擬し、本体の欠けたmoovが正常判定されることを確認した。
- BUG-06はコード上で確認した。通信を停止させた再現テストは未実施。

これらの再現確認は既存テストに追加されていない。実装時に回帰テストとして残す。

## 3. 不具合対応

### BUG-01: 接続処理の競合

**現象:** Aへの接続応答を待つ間にBを選び、Aの処理が後から完了すると、選択中はBなのに入力先がAになる。表示の開始順もB→Aになる。

**主な対象:** [SimulatorWebviewProvider.ts](../src/webview/SimulatorWebviewProvider.ts) の `startCaptureForDevice`、接続を開始する各呼び出し元、切断・非表示・破棄処理。

**方針:** 接続試行に世代番号を付け、共有状態を更新する前に現在の試行か確認する。端末IDの比較だけではA→B→Aの競合を区別できないため、世代で判定する。

- 新しい接続・切断・非表示・破棄で進行中の試行を無効化する。
- デバイス情報、agent導入、入力初期化、映像開始など、待機後の処理とコールバックを確認する。
- 古い試行が生成したコントローラー・キャプチャだけを解放し、新しい試行のリソースを触らない。
- 同じ端末への再接続で入力を再利用する既存動作は維持する。

**完了条件:**

- [ ] A→BおよびA→B→Aを応答順を逆転させて実行しても、選択・表示・入力が最後の接続試行に一致する。
- [ ] 接続待ち中に切断・非表示・破棄しても、遅い応答で接続が復活しない。
- [ ] 古い試行のプロセス・タイマー・イベントリスナーが残らない。

### BUG-02: 録画開始待ち中の状態変更

**現象:** `startScreenRecord()` の完了前は録画セッションが登録されていない。Aの開始待ち中にBへ切り替えると、切替時に停止されず、遅い応答後にAの録画が登録される。

**主な対象:** [SimulatorWebviewProvider.ts](../src/webview/SimulatorWebviewProvider.ts) の `toggleRecording`、ビュー録画開始、録画停止、端末切替・非表示・破棄処理。

**方針:** 開始中から録画対象・クライアント・保存先を追跡し、開始結果が返った時点でも試行の有効性を確認する。

- 保存ダイアログの待機も含め、開始操作を二重に受け付けない。キャンセル・失敗時は必ず解除する。
- 開始中に状況が変わったらキャンセル要求を記録する。開始が成功して返ってきた場合は、開始に使ったクライアントで元の端末の録画を停止する。
- RPCの待機中断は、端末側の録画停止を保証しない。応答のタイムアウト時も成功・失敗を決めつけず、停止・状態確認の可否を既存APIで確認する。
- ビュー録画でも開始応答、writerの所有者、古い応答・チャンクの扱いを確認する。必要なら録画試行IDで関連付ける。
- 停止に失敗した場合は対象を追跡したままエラーと再試行を提示する。拡張終了時は既存の待機上限を守り、停止を確認できなかった事実をログに残す。

**完了条件:**

- [ ] 開始応答待ち中の端末切替・非表示・破棄で、旧端末の録画を追跡せず放置しない。
- [ ] 保存ダイアログ中や開始処理中の連打で、録画・writer・保存先を二重作成しない。
- [ ] キャンセル後の遅い成功応答・失敗応答が、新しい録画の状態を上書きしない。
- [ ] 停止失敗を成功表示せず、通常操作中は再試行できる。

### BUG-03: Android入力コマンドの失敗検知

**現象:** 入力コマンドの後に無条件で完了マーカーを出しており、コマンドが失敗しても `AdbTouch.send()` が成功を返す。標準エラーも破棄される。

**主な対象:** [AdbTouch.ts](../src/input/AdbTouch.ts)、[AndroidBackend.ts](../src/input/AndroidBackend.ts)。

**方針:** 完了通知に実行結果を含め、複数コマンドの途中の失敗も検出する。失敗時は既存のmobilecli経路への切替を利用する。

- 完了通知はチャンク分割されても解析できる形にする。待機数・バッファ・時間の上限を維持する。
- 一部だけ成功したジェスチャーを丸ごと再送すると二重入力になり得る。押下済みの場合の指の解放と、後続操作のフォールバックを区別する。
- 失敗理由は診断に必要な範囲だけ記録し、入力内容をログへ出さない。

**完了条件:**

- [ ] 正常終了・非ゼロ終了・途中のコマンドだけの失敗を区別する。
- [ ] タイムアウト・プロセス終了で待機中の呼び出しが解決する。
- [ ] 非対応コマンドなどで失敗しても、後続操作を使える経路へ切り替えられる。
- [ ] 押しっぱなしや、成功済み操作の不用意な二重実行を防ぐ。

### BUG-04: 画面サイズの持ち越し

**現象:** 新しい端末の `device.info` が失敗しても旧端末の `screenSize` が残り、Android・WDA入力が誤った座標へ変換される。

**主な対象:** [SimulatorWebviewProvider.ts](../src/webview/SimulatorWebviewProvider.ts) の `applyScreenSize` と接続処理。

**方針:** 端末変更時に旧サイズを破棄する。幅・高さが正の有限数であることを検証し、有効なサイズが取れるまでサイズに依存する入力を送らない。映像は表示可能なら継続し、操作できない理由を知らせる。

**完了条件:**

- [ ] 別端末の情報取得失敗で旧サイズを使わない。
- [ ] サイズ欠落・0・負数・非数値を座標変換に使わない。
- [ ] 再取得成功で操作が復旧する。
- [ ] 遅れて返った旧端末の情報が新端末のサイズを上書きしない（BUG-01と共通で検証）。

### BUG-05: MP4の正常判定

**現象:** `moov` 識別子を見つけた時点で正常と判定し、そのボックスの宣言サイズや本体の存在を確認しない。

**主な対象:** [RecordingFile.ts](../src/simulator/RecordingFile.ts)、[recording-file.test.js](../test/recording-file.test.js)。

**方針:** 成功を返す前に通常・拡張サイズとファイル境界を確認する。既存の読み込み量・走査回数の上限は維持する。全ファイル読み込みや動画デコード依存は追加しない。

**完了条件:**

- [ ] 「サイズ4096のmoovを宣言しているが8バイトしかない」ファイルを拒否する。
- [ ] 拡張サイズのヘッダ不足、最小ヘッダ未満のサイズ、ファイル末尾を越えるボックスを拒否する。
- [ ] 正常な録画の検査と既存のWebM検査を壊さない。
- [ ] 文言・コメントで、この検査がコンテナ構造の簡易検査であり、完全な再生保証ではないことを明確にする。

### BUG-06: 入力RPCのタイムアウト

**現象:** タップ・ジェスチャー・ボタン・通常の文字入力では明示的なタイムアウトがなく、応答を待つ入力処理が長時間止まる可能性がある。

**主な対象:** [JsonRpcClient.ts](../src/utils/JsonRpcClient.ts)、[MobileCliClient.ts](../src/utils/MobileCliClient.ts)、入力側の呼び出し元。

**方針:** RPC共通層に既定の待機上限を設定する。初期案は15秒とし、長いジェスチャーや文字入力に必要な時間を確認して調整する。録画・起動など既存の個別指定は優先する。

- 全呼び出し元を確認し、正常な長時間操作を短い既定値で打ち切らない。
- タイムアウト後は入力キュー・押下状態を回復可能にする。
- タイムアウトは「未実行」と同義ではない。タップ・文字入力を自動再送しない。

**完了条件:**

- [ ] 応答しないRPCが指定時間内に失敗し、後続処理が待ち続けない。
- [ ] 個別のタイムアウト指定が維持される。
- [ ] タイムアウト後の新しい操作を受け付け、入力内容をエラーに含めない。

## 4. FEAT-01: 接続診断

### 利用者向けの動作

コマンドパレットと接続エラー時の導線から「接続診断」を開く。VS Code標準のQuick Pickなど既存UIで結果を表示し、専用の複雑な画面は作らない。

| 項目 | 表示する内容 |
|---|---|
| 接続対象 | 端末名、OS、起動状態、現在の接続段階 |
| mobilecli | 同梱バイナリの利用可否、サーバー到達性、一覧取得の成否 |
| 入力 | 現在の経路、フォールバックの有無と理由、必要な画面サイズの取得状況 |
| iOS Simulator | サイドカーの存在・稼働状態、既に検知した初期化失敗 |
| Android | adbの解決結果、対象端末の検出状況、既に検知した入力経路の失敗 |
| 映像 | 使用経路、受信状況、直近の失敗 |

結果は「正常／問題あり／未確認／対象外」を区別する。プロセスが存在するだけで入力や映像を正常と断定しない。静止画面では新しいフレームが来ないため、利用できる生存通知やキャプチャ状態も考慮する。

原因ごとに「再試行」「ログを開く」と具体的な復旧手順を示す。例: adbが見つからない、端末が停止中、HID初期化失敗で互換経路へ切り替わっている。

### 実装方針

- `MobileCliServer`、`SimulatorInputController`、`AdbTouch`、キャプチャ層が既に持つ情報を再利用する。
- 保持する履歴は直近の失敗など必要最小限とし、無制限なイベント履歴を追加しない。
- 実行時に必要な読み取り確認だけをタイムアウト付きで行う。常時の追加ポーリングはしない。
- 診断操作では端末起動・agent導入・サーバー再起動・テスト入力を行わない。復旧操作は既存の明示的な操作へつなぐ。
- トークン付きURL、入力文字列、クリップボード内容は結果に含めない。初期版は診断結果の外部送信や自動アップロードを持たない。
- 新しいUI文言は英語・日本語・簡体字中国語の既存翻訳に追加する。

### 完了条件

- [ ] 未接続状態でも診断を開ける。
- [ ] サーバー未到達、端末未検出、adb不在、HID降格をそれぞれ説明できる。
- [ ] 未確認と正常を区別し、診断が応答待ちで終わらなくなることがない。
- [ ] 診断を閉じても新しいプロセス・タイマーを残さない。
- [ ] 診断だけで端末やサービスの状態を変更しない。
- [ ] 秘密情報が結果・ログに含まれないことをテストする。

## 5. FEAT-02: 録画時間・停止処理中の表示

### 利用者向けの動作

既存のRecボタン付近に次の状態を表示する。

| 状態 | 表示例 | 操作 |
|---|---|---|
| 待機 | `Rec` | 開始できる |
| カウントダウン | 既存の秒読み | 二重開始を受け付けない |
| 開始待ち | `録画を開始しています…` | 二重開始を受け付けない |
| 録画中 | `録画中 02:15 / 10:00（残り07:45）` | 停止できる |
| 停止・書き出し中 | `録画を保存しています…` | 開始・停止の連打を受け付けない |
| 停止失敗 | `停止を確認できませんでした` | 対象を保持し、停止を再試行できる |
| 完了 | 既存の保存結果通知 | 次の録画を開始できる |

残り時間は10分の時間上限までの目安。ビュー録画は容量上限で先に止まる場合があることをツールチップなどで説明する。保存処理の完了率は取得できないため、架空のパーセント表示はしない。

### 実装方針

- BUG-02で整理した録画状態を表示にも使用する。表示専用の別の状態管理を増やさない。
- 開始確認時刻と時間上限を拡張ホストで保持し、既存の録画状態メッセージとwebview復元処理で送る。開始確認前の秒読み・応答待ちは経過時間に含めない。
- 時間は表示回数の加算ではなく、開始時刻との差から算出する。実際の端末側開始時刻が取得できない場合は、ホストが開始を確認した時刻を基準とする。
- webviewは表示中・録画中だけ約1秒間隔で表示を更新する。毎秒のログや新しいホスト側ポーリングは追加しない。
- 停止要求時に保存中へ移り、最終チャンク・ファイルclose・検査が終わるまで完了扱いにしない。
- webview再作成時はホストの状態で復元する。既存仕様どおり中断するビュー録画を、継続したように表示しない。
- 状態変化は読み上げ可能にするが、毎秒の時間更新を読み上げ続けない。翻訳は既存3言語へ追加する。

### 完了条件

- [ ] カウントダウン・開始待ち・録画中・保存中・停止失敗を見分けられる。
- [ ] 描画が遅れても経過時間が更新回数に依存してずれない。
- [ ] 停止処理中に次の録画を開始できない。
- [ ] 保存成功はファイルの書き出しと検査が終わった後だけ表示する。
- [ ] 停止失敗・容量上限・時間上限・ビュー消失時に表示が実際の状態と一致する。
- [ ] 非表示・停止・破棄で表示更新タイマーを解放する。

## 6. 実装順序と検証

| 順序 | 対応 | 理由 |
|---|---|---|
| 1 | BUG-01 + BUG-04 | 操作対象と座標の正しさを先に確保する |
| 2 | BUG-02 | 録画開始・停止の所有者を明確にする |
| 3 | BUG-03 + BUG-06 | 入力の失敗と待機上限を揃える |
| 4 | BUG-05 | 保存結果の誤判定を修正する |
| 5 | FEAT-01 | 修正後の接続・入力状態を診断に利用する |
| 6 | FEAT-02 | 整理した録画状態を利用者に表示する |

各単位で関連する既存テストへ回帰ケースを追加する。Node標準のテストと既存のVS Codeスタブを使い、競合は任意に解決できるPromiseで再現して実時間の長い待機を避ける。

実装後は以下を確認する。

- [ ] `npm run typecheck` と `npm test` が成功する。
- [ ] 追加文言の翻訳・コマンド宣言・webviewの状態復元を確認する。
- [ ] Extension Development Hostで接続切替、診断、録画開始／停止／失敗表示を確認する。
- [ ] 利用可能なiOS Simulator・Android環境で入力と録画を確認し、検証したOS・端末・入力経路を記録する。
- [ ] 長い開始待ち、応答なし、端末切替、非表示、破棄のケースをモックで補完する。
- [ ] `view` / `device` の両録画経路と、直結配信からビュー録画への切替を確認する。
- [ ] READMEとCHANGELOGの更新は実装完了時に行い、未検証の環境を検証済みと記載しない。
